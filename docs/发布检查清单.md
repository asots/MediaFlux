# MediaFlux 镜像与版本发布检查清单

## 1. 发布原则

- 正式发布由推送 `v<SemVer>` tag 触发；当前 Docker 工作流未提供 `workflow_dispatch` 手动触发入口。
- Docker 镜像发布 `linux/amd64` 与 `linux/arm64` 双架构。
- GHCR 镜像使用去掉 `v` 前缀的精确版本标签（如 `1.2.0`）；稳定版同时更新系列标签（如 `1.2`）与 `latest`，且不会向旧版本回退。
- 普通升级与容器重启必须保证挂载卷中的数据库、配置、Token、STRM 和整理任务数据完整保留。

## 2. 发布前检查

1. `main` 工作区干净，全量自动化测试为 0 failure / 0 error。
2. 运行 `compileall` 与诊断自检：`python -m compileall -q app` 与 `python mediaflux.py doctor`。
3. 检查 `requirements.txt` 与 `requirements-release-runtime.lock` 依赖锁一致。
4. 检查 Dockerfile 运行时依赖锁、内置 `/usr/bin/ffprobe`、权限初始化入口、默认 NAS 兼容模式与可选 PUID/PGID 降权；容器内执行 `ffprobe -version` 和 `gosu --version` 必须成功。
5. 确认 `app.__version__` 与准备创建的 `v<SemVer>` tag 完全一致，`CHANGELOG.md` 中有对应日期和非空版本章节；变更记录按上一个正式 tag 到实际候选提交的真实区间核对，不改写已发布区间。
6. 记录最终候选 commit 与验收镜像的源码/构建信息；验收后如修改源码、版本或发布日期，重新核对候选范围和相关门禁，不能拿旧镜像结果代替新提交验收。
7. 正式发布前先推送已验收的 `main`，再对准确候选提交创建并推送版本 tag。工作流要求 tag 目标已包含在 `origin/main`；不要只推送一个尚未进入远端 main 的 tag，也不要覆盖已有正式 tag。
8. 本地 amd64 验收不等于 arm64 已验收；正式提升精确版本、系列及 `latest` 标签前，仍须等待 CI 的双架构 manifest、逐架构版本信息与启动冒烟检查通过。

## 3. 发布交付物

- **GHCR 容器镜像**：
  - `ghcr.io/li88iioo/mediaflux:<SemVer-without-v>`（多架构 manifest：`linux/amd64` + `linux/arm64`）
  - `ghcr.io/li88iioo/mediaflux:<major.minor>`（稳定版系列标签，如 `0.1`）
  - `ghcr.io/li88iioo/mediaflux:latest`（稳定版自动更新）
- **版本元数据**：
  - `BUILD-INFO.json`、`RELEASE-NOTES.txt`

## 4. 镜像验收

1. 容器运行 `python mediaflux.py version --json`，确认版本号、commit hash 与 package 为 `docker`。
2. 容器启动探针：`/healthz` 与 `/readyz` 均返回 HTTP 200。
3. `doctor --json` 能正确检查环境与权限。
4. 容器挂载已有宿主机 `./db` 数据卷启动，确认历史数据完整加载且无损。

## 5. 升级与回退

1. 按本版 CHANGELOG 的升级说明确认完整 schema 跨度及功能兼容边界，不只测试上一开发提交的 schema。例如 v0.1.11 的正式 schema 为20，v0.1.12 为27。
2. 升级前保留完整数据目录与备份；自动迁移前备份仍须能通过大小、哈希及 SQLite 完整性校验。不要用真实生产数据卷开展故障注入。
3. 回退时先停止新版本，使用离线恢复流程恢复升级前的数据库和相关配置，再启动匹配的旧版本。不能直接让旧程序打开更高 schema 的库，也不要在恢复后先启动新版本再次触发升级。
4. v0.1.12 的 Agent 已切换到新 Kernel：旧 Agent 对话不自动投影到新历史列表，旧 Agent 待确认操作需要重新发起并确认。保留旧表和备份不代表可以盲目续接或执行旧票据；传统 Telegram 确认仍按各自合同处理。
